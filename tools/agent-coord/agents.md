# Shared CPU, RAM and agent messages (agent-coord)

Several agents share this computer. Coordinate heavy work through the `agent-coord` user service (`agent-coord --help`):

- **Before anything heavy** (more than 2 cores or 2 GB for more than a few minutes: alignment, variant calling, full test suites, big builds), run it through `agent-coord run --cores MIN:MAX --mem SIZE --label "what" -- COMMAND`, e.g. `--cores 2:8`.
  - Use MIN:MAX for everything except timing runs. Fairness between projects (the git repository with all its worktrees; a `--project NAME` counts separately only if configured) applies to elastic (MIN:MAX) leases: they share the machine fairly between active projects and can use every core when the others are idle. It starts as soon as MIN cores are free and caps the command at its grant and at SIZE of RAM. Expect to be shrunk while it runs (toward MIN, never below, never killed) when another project needs its fair share or when it uses under half its grant, and to grow back later.
  - Give the command's tools `COMPUTE_LEASE_CORES` threads. Long jobs that can adapt poll line 1 of the file named by `COMPUTE_LEASE_FILE` for the current count (line 2 is JSON with min, max, granted, reason); the cap is already applied, so a tool with a fixed thread count is throttled, not broken. `--notify-signal` also sends SIGUSR1 on each change, but that terminates a command without a SIGUSR1 handler (including `sh -c`, `make` and other wrappers): use it only for programs that handle it.
  - A single number (`--cores N`) is a fixed lease, never shrunk: keep fixed, `--exclusive-lock` and `--exclusive` leases for timing runs. Fixed and timing leases are admitted as before, and a project that holds the machine with fixed jobs keeps it until they end; a timing run may shrink other projects' elastic leases down to their MIN; asking a big fixed size never gets more than asking MIN:MAX.
  - Add `--expect 10m` when you know the run time; otherwise it learns from completed runs for your agent/label (30m initially). Jobs may pass a capacity-blocked head only if they finish before its projected start or leave its capacity free. Overruns that delay the head pause new backfill and notify their agent; estimates do not kill jobs.
- `agent-coord check --cores N|MIN:MAX --mem SIZE` says whether a job that size may start now. `agent-coord status` shows who holds what.
- Use `--io` for downloads, uploads and disk-streaming jobs; it defaults to 1 core and 512M.
- **Timed or performance runs:** for a GPU timing run use `--exclusive-lock gpu` (exclusive on the GPU, its cores guaranteed, CPU-only work keeps running beside it), plus `--headroom N` to keep N more cores unclaimed and bound timing noise. Use whole-machine `--exclusive` only when nothing else may run; small jobs (≤2 cores, ≤6G) still start during its first 30 min of waiting. A job started without a lease can be registered with `agent-coord hold … --pid PID`.
- `agent-coord history [--since 6h] [--json]` shows lease events with wait and run times and why requests waited.
- **Messages:** read `agent-coord inbox` at the start of work, before heavy jobs, and when a lease waits a long time. Use `agent-coord send --to AGENT|all "…"` to tell others about things that affect them, such as long IO, VM ownership or when you will finish.
- Reserve disk for big outputs and temp files with `--disk PATH:SIZE`, sized for the job's peak (for example `--disk /home:150G` for a 30x realign).
- Own things that can't be shared (a VM, the GPU, the NAS link during a timed run) with `agent-coord lock NAME --reason "…" [--pid PID]` until `unlock NAME`, or pass `--lock NAME` to `run`. Check `status` before touching something another agent owns.
- Your name is your git worktree's folder name; use `--as NAME` to set another.
- If the service is down, start it with `systemctl --user start agent-coord`; do not work around it.
